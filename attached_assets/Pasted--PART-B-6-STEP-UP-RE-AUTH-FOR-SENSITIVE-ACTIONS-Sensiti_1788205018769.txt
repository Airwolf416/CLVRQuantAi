━━━ PART B.6 — STEP-UP RE-AUTH FOR SENSITIVE ACTIONS ━━━
Sensitive actions require fresh password confirmation regardless of session age.

1. DISCOVERY: locate the handlers for (a) email/account-identity changes,
   (b) password change, (c) any Stripe payment-method or billing-portal
   endpoints, (d) account deletion if present. Report what exists — do not
   invent endpoints that aren't there.

2. Server: middleware requireRecentAuth(maxAgeMinutes = 10):
   - Session gains a lastPasswordConfirmAt timestamp, set at login and on
     successful re-confirmation.
   - If older than 10 minutes when a sensitive route is hit, respond 403
     with JSON { code: "REAUTH_REQUIRED" }. Do not destroy the session —
     the user stays signed in everywhere else.
   - New endpoint POST /api/session/confirm-password: verifies current
     password (bcrypt compare against existing hash), refreshes
     lastPasswordConfirmAt on success. Rate-limit it same as login
     (10 / 15 min per IP) — this endpoint is itself a password oracle.
   - Apply requireRecentAuth to: email change, password change, payment
     method/billing endpoints, account deletion. Nothing else — trading
     features, AI features, and settings toggles stay friction-free.
   - Note: for Stripe billing-portal session creation, the check wraps the
     portal-session creation call; once the user is in Stripe's hosted
     portal, Stripe's own auth applies.

3. Client: on 403 REAUTH_REQUIRED, show a small modal: "Confirm your
   password to continue" with a single password field. On success, retry
   the original action automatically so the user doesn't lose their input.
   On cancel, return to where they were with no state loss. Modal follows
   the Part C motion rules (fade/scale entrance, reduced-motion respected).

4. Log every step-up challenge and outcome (userId, route, success/fail,
   timestamp) to the existing server logging — useful audit trail, no PII
   beyond what's already logged.

━━━ ADDITIONAL ACCEPTANCE CRITERIA ━━━
11. Changing account email 11+ minutes after login triggers REAUTH_REQUIRED;
    confirming the password completes the original change without re-entry
    of the form data.
12. Wrong password on confirm-password fails closed, counts toward the rate
    limit, and never reveals whether the account/email exists.
13. Normal trading and AI flows never encounter the re-auth modal.
14. lastPasswordConfirmAt refreshes on login, so a user acting within 10
    minutes of signing in sees zero added friction.
